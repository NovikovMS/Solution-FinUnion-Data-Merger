# Целевая архитектура данных

Диаграмма: [`diagrams/target-data-architecture.mmd`](diagrams/target-data-architecture.mmd).

Дерево решений по дальнейшему росту: [`diagrams/scalability-decisions.mmd`](diagrams/scalability-decisions.mmd).

## Архитектурная цель

Через 12 месяцев объединённый банк использует общую платформу данных, но сохраняет разделение ответственности:

- операционные системы выполняют клиентские и финансовые транзакции.
- MDM, RDM и Product Catalog управляют золотыми и справочными данными.
- Integration Layer связывает домены через API, события и CDC.
- Lakehouse хранит полную историю и большие событийные наборы.
- DWH публикует сверенные данные для BI и обязательной отчётности.
- DataHub показывает владельцев, контракты, качество и lineage.

Ни DWH, ни Lakehouse, ни Integration Layer не становятся мастерами счетов, платежей и операций. Авторитетное состояние сохраняется в профильных доменных OLTP.

## Основной поток данных

1. OLTP публикует доменные события в Kafka и технические изменения через CDC.
2. MDM, RDM и Product Catalog публикуют версии золотых данных и справочников.
3. Ingestion сохраняет неизменяемую копию сообщения или записи в зоне `raw`.
4. Слой `standardized` нормализует типы, идентификаторы, время, валюты и коды.
5. Слой `curated` объединяет сущности по глобальным ключам и формирует доменные наборы.
6. Publication Gate проверяет полноту, ссылочную целостность и финансовые суммы.
7. Сертифицированные данные загружаются в PostgreSQL DWH и становятся доступны BI.
8. Trino предоставляет SQL-доступ к детальной истории и data products в Iceberg.
9. Каждый шаг публикует metadata и lineage в DataHub.

## Синхронный и асинхронный обмен

Синхронные API применяются для команд и запросов, где пользователь ожидает немедленный результат. Примеры включают открытие счёта, проверку статуса продукта и получение глобального идентификатора.

События Kafka применяются для распространения подтверждённых изменений между доменами. Consumer обрабатывает событие независимо и повторяет попытку без блокировки producer.

CDC используется для поставки изменений в аналитический контур. CDC не заменяет доменное событие, потому что отражает техническое изменение таблицы, а не всегда бизнес-смысл.

Batch используется для исторических выгрузок, контрольных срезов, пересчёта витрин и обязательной отчётности.

## Надёжность и восстановление

- Каждый поток имеет owner, schema version, idempotency key и correlation ID.
- Kafka хранит события достаточно долго для replay в пределах согласованного операционного окна.
- Raw-слой позволяет полностью пересобрать standardized, curated и DWH.
- Airflow поддерживает retry, backfill и запуск с контрольной точки.
- Финансовые пайплайны сверяют количество записей, обороты и остатки.
- Публикация BI и отчётности блокируется при критической ошибке качества.
- Конкретные RPO и RTO утверждаются после Business Impact Analysis.

## Безопасность

- Сервисные соединения используют mTLS и короткоживущие учётные данные.
- ПДн шифруются и доступны по RBAC/ABAC с учётом цели обработки.
- PAN покидает PCI-контур только в токенизированном или маскированном виде.
- Raw, standardized, curated и DWH имеют раздельные политики доступа.
- Тестовые среды используют синтетические или необратимо обезличенные данные.
- DataHub содержит метаданные, но не значения чувствительных полей.
- Аудит фиксирует доступ, изменение политики, публикацию и повторную обработку.

## Владение

Доменные Data Owners отвечают за семантику и допустимое использование данных. Data Stewards управляют качеством и конфликтами. Platform Team отвечает за Kafka, Airflow, Iceberg, Trino и DataHub как технические сервисы. Наличие общей платформы не переносит бизнес-владение от домена к платформенной команде.

## Целевое состояние через 12 месяцев

К концу целевого периода платформа должна обеспечивать устойчивую ежедневную эксплуатацию, а не только наличие установленных компонентов:

- PostgreSQL DWH обслуживает сертифицированные витрины и отчётность в согласованном окне.
- Iceberg Lakehouse принимает полную историю, CDC, события и архивные поставки.
- Schema Registry блокирует несовместимые изменения контрактов.
- Iceberg Catalog обеспечивает согласованные commits и восстановление metadata.
- Table Maintenance выполняет compaction, snapshot expiration и orphan file cleanup.
- Kafka, Airflow и Trino имеют раздельные ресурсы для критических и некритических нагрузок.
- MDM выдерживает рабочий поток match/merge без неконтролируемого роста ручной очереди.
- DataHub показывает lineage для всех критичных наборов от источника до отчёта.
- Publication Gate не допускает BI и регуляторную публикацию при ненулевом расхождении.

## Архитектурный запас на горизонте 3–5 лет

Горизонт 3–5 лет не является утверждённым целевым состоянием. Он используется для проверки, можно ли развивать платформу без изменения бизнес-границ и повторного объединения данных.

Базовые решения сохраняются:

- профильные домены остаются владельцами данных.
- Kafka остаётся транспортом событий, а Iceberg — долговременной историей.
- DWH остаётся сертифицированной проекцией, пока укладывается в эксплуатационные ограничения.
- DataHub и контракты сохраняют единый governance при росте числа команд.

Дополнительные компоненты вводятся только при подтверждённой потребности:

- выделенный Stream Processor — при устойчивом росте event lag и сложной stateful-обработке.
- read replicas PostgreSQL — при конкуренции BI с загрузочными процессами.
- hot/cold split — при приближении DWH к пределу ёмкости или окна загрузки.
- columnar/MPP DWH — если PostgreSQL перестаёт обеспечивать certified workload даже после архивирования и агрегирования.
- отдельный immutable regulatory publish — при необходимости воспроизводить каждый опубликованный отчёт независимо от текущего DWH.
- отдельный token vault — если масштаб карточных и связанных аналитических сценариев требует централизованного управления токенами.
- multi-region DR — по результатам BIA и проверок восстановления.

## Красные линии

Рост не является основанием ослаблять финансовую корректность:

- ненулевое reconciliation блокирует публикацию затронутого набора.
- false merge выше утверждённого порога останавливает автоматическое объединение.
- отчёт без воспроизводимого snapshot и lineage не считается сертифицированным.
- потеря события не компенсируется приблизительным агрегатом.
- чувствительные данные не выводятся из защищённой зоны ради ускорения аналитики.
