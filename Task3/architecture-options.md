# Сравнение архитектурных вариантов

## Критерии

Варианты оцениваются по скорости запуска, финансовой корректности, масштабу истории, поддержке событий, управляемости, стоимости эксплуатации и соответствию организационной зрелости объединённого банка.

| Вариант | Почему не выбран основным |

## Решение

Выбран **гибрид DWH + Lakehouse с принципами Data Mesh**.

### PostgreSQL DWH

Используется для стабильных фактов, измерений, сертифицированных витрин, управленческой и регуляторной отчётности. Он обеспечивает понятную SQL-модель и быстрый результат для контролируемого объёма.

### Data Lakehouse

Используется для raw-истории, CDC, событий, архивных выгрузок, документов и больших аналитических наборов. Apache Iceberg обеспечивает табличную семантику, а Trino предоставляет SQL-доступ.

### Data Mesh

Используется как операционная модель:

- домен владеет смыслом и качеством data product.
- общая платформа предоставляет ingestion, storage, compute, каталог и безопасность.
- federated governance задаёт обязательные контракты, идентификаторы, классификацию и lineage.
- физическая инфраструктура остаётся общей, чтобы не дублировать платформу в каждом домене.

## Почему гибрид подходит

1. PostgreSQL DWH позволяет быстро собрать согласованные витрины клиентов, счетов, продуктов и операций.
2. Lakehouse снимает ограничения по истории и событиям без переноса аналитической нагрузки в OLTP.
3. Raw-слой сохраняет исходные записи FU/RB и делает преобразования воспроизводимыми.
4. DWH получает только сертифицированные данные и остаётся стабильным для отчётности.
5. Доменные data products согласуются с BIAN и назначенными Data Owners.
6. Компоненты можно вводить поэтапно без остановки клиентских сервисов.

## Условия успеха

- единые `customer_id`, `product_id` и таблицы source links.
- Schema Registry и совместимые data contracts.
- контроль качества до публикации.
- автоматический lineage в DataHub.
- эксплуатационные владельцы Kafka, Airflow, Iceberg, Trino и PostgreSQL.
- доменные Owners и Stewards с измеримыми SLA.
- разграничение ресурсов интерактивной аналитики, batch и регуляторных расчётов.

## Когда PostgreSQL перестаёт быть достаточным

Переход к columnar/MPP рассматривается только после подтверждения, что оптимизации PostgreSQL не возвращают требуемый запас.

Последовательность решения:

1. Проверить планы запросов, partition pruning, индексы, bloat и настройку autovacuum.
2. Вынести BI-чтение на replicas и отделить его от загрузки.
3. Оставить в PostgreSQL ограниченное hot window и агрегаты.
4. Перенести историческую детализацию в Iceberg с доступом через Trino.
5. Провести нагрузочный тест на целевом профиле.
6. Только при сохранении ограничения выбрать columnar/MPP, не меняя контракты data products и Publication Gate.

Сам календарный срок не является основанием миграции. Решение принимается по измеренному исчерпанию ёмкости, окна загрузки или допустимой стоимости.
