# DWH и Data Lakehouse

## Решение по горизонтам

| Горизонт | Основной подход | Назначение |
|---|---|---|
| 3 месяца | PostgreSQL DWH | • Общие измерения клиента, счёта и продукта<br><br>• Факты операций и датированные остатки<br><br>• Минимальные BI-витрины<br><br>• Сверенная управленческая отчётность |
| 12 месяцев | Гибрид PostgreSQL DWH + Iceberg Lakehouse | • DWH для стабильной отчётности<br><br>• Lakehouse для полной истории, событий и архивов<br><br>• Trino для SQL над Iceberg<br><br>• DataHub для общего governance и lineage |

PostgreSQL не заменяется Lakehouse. Каждый компонент получает собственный класс нагрузки, а данные переходят в DWH только после стандартизации и проверки.

## Роль Apache Iceberg

Apache Iceberg задаёт открытый table format поверх object storage:

- атомарные коммиты и согласованные snapshots.
- schema evolution без ручного переписывания всей таблицы.
- partition evolution при изменении профиля запросов.
- time travel для воспроизводимости и расследований.
- hidden partitioning, уменьшающий зависимость запросов от физического layout.
- совместную работу batch и streaming-писателей через контролируемые commit-процессы.

Iceberg не решает качество, каталогизацию и безопасность автоматически. Эти обязанности остаются у пайплайнов, Data Quality Gate, IAM и DataHub.

## Роль Trino

Trino предоставляет SQL-доступ к Iceberg и curated data products:

- интерактивный анализ большой истории без загрузки всего объёма в PostgreSQL.
- федеративные запросы во время контролируемого перехода.
- доступ BI, Risk и Data Science через отдельные resource groups.
- единый SQL-интерфейс для доменных curated-наборов.

Trino не используется для транзакционных команд и не становится системой хранения. Тяжёлые запросы ограничиваются квотами, timeouts, concurrency limits и workload management.

## Физическая организация Lakehouse

| Зона | Формат | Разбиение | Retention | Правило публикации |
|---|---|---|---|---|
| `raw` | Iceberg / Parquet с исходным payload | • `source_system`<br><br>• `ingestion_date` | По классу данных и правовым требованиям | После технической проверки доставки и хеша |
| `standardized` | Iceberg / Parquet с канонической схемой | • `source_domain`<br><br>• `business_date` | Полная требуемая история | После schema, validity и reference checks |
| `curated` | Iceberg / Parquet по data product | • Домен<br><br>• Бизнес-дата<br><br>• Оптимизированный partition key | По контракту data product | После доменных проверок и reconciliation |
| PostgreSQL DWH | Реляционные fact/dimension | • Дата для крупных фактов<br><br>• Индексы по surrogate key | Регламентированный период | После Publication Gate и сертификации batch |

Конкретное partitioning выбирается по измеренным объёмам и запросам. Высокая кардинальность `customer_id` или `transaction_id` не используется как прямой partition key.

## Загрузка в PostgreSQL DWH

1. Airflow фиксирует snapshot curated-таблиц и `batch_id`.
2. Trino или выделенный ELT-job формирует набор для загрузки.
3. Stage-таблицы принимают данные без публикации пользователям.
4. Проверки сравнивают record count, суммы, валюты и ссылки на измерения.
5. SCD-измерения обновляются по business key и периоду действия.
6. Факты загружаются идемпотентно по source key.
7. Успешный batch атомарно переводит витрины в статус `certified`.
8. DataHub получает lineage от Iceberg snapshot до DWH-таблицы и BI-витрины.

## Ограничения и меры

| Ограничение | Риск | Мера |
|---|---|---|
| PostgreSQL DWH имеет ограничение вертикального масштаба | Рост истории замедляет загрузку и запросы | • Оставлять детальную историю в Lakehouse<br><br>• Партиционировать крупные факты<br><br>• Использовать агрегаты и materialized views<br><br>• Архивировать закрытые периоды |
| Small files в Lakehouse | Медленное планирование и чтение | • Compaction по расписанию<br><br>• Контроль размера файлов<br><br>• Ограничение частоты commits<br><br>• Мониторинг количества файлов |
| Поздние и изменённые события | Расхождение DWH и истории | • Watermark<br><br>• Допустимое окно lateness<br><br>• Пересчёт затронутых партиций<br><br>• Версионирование факта |
| Schema evolution источников | Поломка consumers | • Schema Registry<br><br>• Compatibility checks<br><br>• Контрактные тесты<br><br>• Параллельная версия |
| Федеративные запросы Trino | Непредсказуемая нагрузка | • Resource groups<br><br>• Query limits<br><br>• Отдельные compute pools<br><br>• Предрасчёт частых наборов |
| Дублирование данных между Lakehouse и DWH | Неясный источник аналитической истины | • Назначить DWH сертифицированным источником отчётности<br><br>• Curated считать детальным продуктовым слоем<br><br>• Публиковать статус и lineage в DataHub |
| Чувствительные данные в raw | Расширенный риск доступа | • Отдельные зоны и ключи<br><br>• ABAC<br><br>• Токенизация<br><br>• Запрет чувствительных значений в каталоге и логах |

## Критерий размещения нового набора

Набор помещается в DWH, если имеет стабильную схему, требуется для повторяемой отчётности и укладывается в контролируемый объём. Набор помещается в Lakehouse, если требуется полная история, высокая гранулярность, schema evolution, повторная обработка или data science. Один набор может существовать в обоих слоях, если curated Iceberg является детальным источником, а DWH — сертифицированной проекцией с явным lineage.
